# Parlay UX evaluation — 2026-08-30

An end-to-end walk of parlay's user journeys, taken from a newcomer's seat by an
agent evaluator (`parlay-ux-eval`, bead `task-pp395`). Method: followed only
what the docs say, against an isolated dev instance (`:45599`, with
`PARLAY_DATA_DIR`/`PAI_DIR`/`HOME`/`PARLAY_STATE_HOME` redirected to scratch and
`PARLAY_HUB_URL` pinned to itself). Anything that could not be exercised without
touching the live install was evaluated read-only and is flagged below. Each
friction point was either fixed on the spot (commit referenced) or recorded
under Unfixed findings.

## What is genuinely good

- **Every verb prints a `Next:` hint.** The CLI teaches its own flow; a
  newcomer never dead-ends. This is the standout UX feature of the whole surface.
- **Refusals explain themselves.** `send` to an unregistered agent says *why*
  (nothing polls the channel), *how to list targets*, and *how to override*
  (`--force`) — a model error message.
- **The safety plumbing is real.** The server prints its data dir at boot; a
  non-default `PARLAY_SERVER` gets its own scoped relay (`srv-<hash>`) with
  clear narration; `sweep` holds rather than guesses.
- **`doctor` failure lines carry their own fix commands.**

## Friction found → fixed in this pass

1. **README Layout table advertised a deleted package.** `packages/cli` was
   removed in T-08 (`871b3f8f` ported `lavish-import` to Go) but the table still
   told newcomers it existed and that `bin/parlay` routes to it. The
   Development section also called `cli` a testable TS package. *Fixed: row
   removed, package list corrected.*
2. **`parlay health` / `doctor` prescribed an impossible eval-engine repair.**
   The fix line was `cd ~/code/parlay/packages/eval-engine && nohup
   ./parlay-eval-engine …` — the author's personal checkout path, and a binary
   that is a gitignored build artifact nothing on a fresh clone builds. A user
   following it verbatim gets two consecutive "No such file or directory"
   errors from a *diagnostic that is telling them how to fix things*. *Fixed:
   both lines now point at `tools/eval-engine/deploy/install.sh` (which builds
   if missing) with the manual `go build` alternative.*
3. **`parlay launch` reported "No agent homes found" over a directory that
   contained one.** A home created by a bare `identity '<fact>'` write (no
   `--register`, so no id/name/color frontmatter) was silently skipped, and
   the listing then denied the home existed — while `sweep`, given the same
   state, correctly said "no launch spec on disk". *Fixed: the listing now
   counts unlaunchable homes, says what they lack, and names the repair
   (`identity --register`); verified end-to-end that the repair produces a
   launchable `[live]` listing. Test added.*

## Unfixed findings (briefing for follow-ups)

- **Bare `listen` still registers before it can stream.** README documents the
  trap: on a fresh clone (no relay binary anywhere) `listen` registers and
  announces *before* discovering the relay can't start, leaving a permanently
  enrolled, deaf agent. Not reproducible on this box (an installed relay binary
  made the scoped-relay path succeed), but the ordering is visible in the
  narration: `registering → announced → arming monitor`. Fix direction:
  probe/start the relay *before* the register+announce calls, or unregister on
  the way out (the current `monitor DOWN` notice is subject to routing caveats
  and leaves the registry entry). Filed as a task bead.
  **→ RESOLVED since this pass (2026-09-03).** The preflight landed for
  `listen` and `claim` (issue #173), and `parlay monitor` was the last entry
  point still missing it — now fixed too. All three preflight before they
  enroll, so a fresh-clone relay failure exits with nothing registered. This
  bullet is kept as the record of how the gap was found; see
  [`monitor.md`](monitor.md) for current behavior.
- **No self-serve panel.** The README is honest that the panel needs a
  same-origin host and that Pulse is private, but the gap remains the biggest
  distance between "what you actually get" and what a clone delivers: the
  advertised voice-first review loop is not reachable from this repo alone.
  Even the "build it and reverse-proxy it yourself" wiring is explicitly
  undocumented. Filed as an idea bead (e.g. teach `packages/server` to
  optionally serve the built bundle same-origin).
  **→ ADDRESSED (2026-09-05).** The idea bead had already been built and the
  docs had not caught up: `packages/go-server` mounts `internal/static` as a
  catch-all *after* the `/api/*` routes, so the server is itself the panel's
  same-origin host — no proxy, no second service. What a fresh clone actually
  hit was narrower and now fixed: `defaultAssetsDir()` only looked relative to
  the executable, and `go run` executes a temp binary under the build cache, so
  the README's own Quickstart command resolved assets to a bare `dist` and `GET
  /` answered `503 assets directory not found: dist`. It now walks up from the
  executable's directory and then from the working directory, the 503 body
  carries the build command, and the README's Requirements section, a new
  Quickstart step 4, `docs/command-server.md` and `docs/api-contract.md`
  describe the panel as served (verified live: `/`, `/parlay-agent.js`,
  `/annotate/pulse-agent.js` and the SPA fallback all 200 from the Quickstart
  command). Still true, and left as-is: `/fleet/` is a *separate* app
  (`packages/webview`) with its own build and copy step, and the voice phrase
  engine is still optional.
- **`health` vs `doctor` disagree on eval-engine severity.** `doctor` calls an
  unreachable eval-engine WARN ("agents don't need it to talk"); `health`
  calls it FAIL and exits 1 — so on a standalone fresh clone, `health` is
  permanently red because an optional voice component is absent. Decision made
  in this pass: left as-is, because on the live install a dead eval-engine is
  exactly what `health` must scream about, and softening it for newcomers
  would mute a real operator signal. Revisit only if standalone users start
  scripting against `health`'s exit code.
  **Still the exit code, but the confusion is gone (addressed 2026-09-05):** the
  severity decision above stands untouched. What changed is everything the line
  tells you *around* it. `health`'s first line is now labelled `server`, never
  `relay` (see below), and a dead engine's FAIL block now states in three lines
  that the engine is optional for the CLI + server, that the CLI / API / panel
  text chat all work without it, and that the line is about the engine rather
  than about your install. The README's Quickstart step 3 note and `parlay health
  --help` say the same, and `--help` no longer advertises the Pulse-wrapper
  check the code has not performed since the TS server was deleted.
- **`health` reported the chat server under the name `relay`.** The probe is a
  single GET of `/api/chat/subscribers` — the chat server and nothing else —
  but it printed `ok relay http://localhost:4242`. parlay ships a *separate*
  relay daemon (`tools/relay`) which `parlay monitor` needs and the README
  tells newcomers to build, so a green "relay" line asserted a healthy daemon
  that was not running at all, while the genuinely-missing relay produced no
  warning here. `doctor` inherited the same conflation twice: the
  server-unreachable fix said "check the Go server and relay are up" (sending a
  newcomer to build the relay when the server was the unreachable thing) and a
  passing enrolment check said "registered as X on the relay". All three now
  say `server`.
- **The identity → handoff → scratchpad recovery chain is one-third private.**
  README sells the three-part chain, but the `handoff` leg (and `identity
  --submit`/`--park` and doctor's `handoff show <id>` advice) rides on the
  author's private beads-store tooling; a clone gets identity + scratchpad
  only. Docs could hedge the chain's third leg the way the panel section
  already hedges Pulse.
  **→ ADDRESSED (2026-09-05).** The `handoff` binary is a brain-federation
  store wrapper (`~/.local/bin/handoff`, a `sh` wrapper pinning the `handoff-`
  store then `exec bd "$@"`, with `~/.pi/agent/bin/handoff` as its symlink —
  the same family as `task`/`inbox`), not a `parlay` verb: `parlay handoff`
  does not exist, and the README's Layout table wrongly listed it as part of
  the CLI surface. Now the README's feature bullet names only the two portable
  legs and a Quickstart callout explains the third; `parlay identity --help`
  gained a SCOPE paragraph; and the three surfaces that *prescribed*
  `handoff create` / `handoff show` now detect the store's absence
  (`resolvehandoff.StoreAvailable`, new) and say so instead of naming a command
  the reader does not have — `identity --submit/--park/--handoff/--dismiss-handoff` explain what the store
  is and echo back the exact invocation that works without it,
  `parlay drawdown` prints a portable tail, and `doctor`'s pointer note drops
  the command while still reporting the pointer. The pinned `> 📎 Handoff:`
  line is deliberately NOT made store-dependent: it is a frozen on-disk format
  that three other packages assert byte-exactly, and a pointer written on one
  machine must read the same on the next.
- Cosmetic, noted only: `GET /api/chat/health` 404s (vitals actually live on
  `/api/chat/subscribers`), which surprises the curl-first newcomer that
  `parlay health` exists for; `doctor`'s eval-engine probe hits the hardcoded
  default port, so an isolated instance's doctor can report PASS off a
  *different* (live) engine on the same host.
