Stop an ambient `$PARLAY_SERVER` from rebinding the production relay and refusing every agent on the box (robots-93xu).

`tools/relay/deploy/install.sh` defaulted its `--server` from the ambient `$PARLAY_SERVER`. The LaunchAgent it installs is a fixed singleton serving the **canonical** runtime dir, and that dir is reserved for the default server (`http://localhost:31337`) — so one install run from a shell that happened to export `http://localhost:4242` permanently rebound the captain's supervised relay, across reboots. Every agent resolving to the canonical dir then found a relay bound to `:4242`, hit the robots-buu8 pre-enroll guard, and was refused. A fleet-wide enrollment outage whose only symptom was agents failing to start; the relay itself looked perfectly healthy the whole time.

Four layers, each of which had to fail for this to happen:

1. **`install.sh` refuses a non-default server.** Exits 2 unless `--allow-non-default-server` is passed, and says so louder when the value came from the environment rather than from `--server`. There is no configuration in which an ambient env var should be able to rebind an installed singleton — and a non-default server needs no install at all, since `ensure-up.sh` starts a scoped relay for it on demand. The guard runs before any side effect (before the Darwin check, the build, and the plist render).
2. **`ensure-up.sh` checks the binding, not just `/health`.** Its fast path returned 0 for any relay answering `/health`, which is a false green: the caller got a success line and then died at its own enroll guard one step later. It now compares the relay's `GET /agents` → `server` against the wanted server and exits **3** — deliberately distinct from 1 ("no relay could be started"), because the two need opposite responses. It does **not** restart the relay: that is a live singleton possibly serving a whole fleet on its own server (robots-mpr3). The message names the bound server, the wanted server, and — when the squatted dir is the canonical one — the `install.sh --server …` repair.
3. **`parlay-monitor.sh`'s advice fits the case.** It recognizes ensure-up's exit 3 and stays quiet rather than contradicting it with "install the relay" (a relay is precisely what is already running). And on its own pre-enroll refusal with *neither* `PARLAY_RELAY_RUNTIME` nor `PARLAY_RELAY_SOCK` set, "unset those overrides" was a dead end — nothing was set, which is exactly why the resolution rule picked the squatted dir. It now names the squatting relay as the fault and prints the repair.
4. **`parlay_relay_installed_plist_server` validated nothing.** PlistBuddy reports its errors ("Error Reading File: …") on **stdout** and can still exit 0, so an unreadable plist came back looking like a server URL. `ensure-up.sh` compared that string against the wanted server, concluded the launchd relay served something else, and quietly declined to use launchd at all — starting an unsupervised duplicate instead. It now only emits something URL-shaped.

Tests: `tools/relay/deploy/install.test.sh` is new (9 cases, hermetic — every case stops either at the guard or at a stubbed non-Darwin `uname`, so nothing is ever built, copied, or loaded). `ensure-up.test.sh` gains the wrong-server and matching-server cases, and its harness was repaired: it pinned `PARLAY_RELAY_RUNTIME` at a temp dir, which the robots-buu8 launchd-matching logic reads as "not the launchd relay's dir", so every launchd case had been falling through to "no relay binary found" — red on `main` before this change. It now stubs `getconf DARWIN_USER_TEMP_DIR` and leaves the override unset, which is the shape production actually runs in. `parlay-monitor.test.sh` gains the no-override case (B6).

**Deploy note:** re-run `tools/relay/deploy/install.sh` after this lands so the installed `lib.sh`/`ensure-up.sh` copies match the repo. To check a box for the squat: `curl -s --unix-socket "$(getconf DARWIN_USER_TEMP_DIR)parlay/relay.sock" http://relay/agents` must report `"server":"http://localhost:31337"`.
